Per-Scan Report

V25 per-scan report: device attribution columns, GET /api/scans/{id}/report endpoint contract, delta classification, and the /scans/:id frontend page.

Section: Scanning · Added: V25

Introduced in V25 / PR #65. The per-scan report lets operators and viewers pull a snapshot of everything a single scan found: metadata, aggregate counts, and a per-device table with delta classification and derived CVEs.

Device attribution columns (V25 schema)

Migration V25__device_scan_attribution.sql adds two nullable BIGINT columns to the device table:

Column Semantics Write rule
discovered_by_scan_id Scan that first discovered the device INSERT-once: set on first INSERT via a scan; never overwritten
last_seen_by_scan_id Scan that most recently observed the device Last-writer-wins: set on every INSERT and UPDATE via a scan

Both columns are NULL for devices that existed before V25 and for devices discovered by non-scan paths (Docker listener, passive ARP, OT probes). No foreign-key constraint is applied — mirrors the loose scan-id referencing used elsewhere in the schema.

How attribution is written

DeviceUpsertService.upsert(Discovery, Long scanId) is the scan-only overload:

  • INSERT (new device): sets discovered_by_scan_id = scanId and last_seen_by_scan_id = scanId.
  • UPDATE (existing device): sets last_seen_by_scan_id = scanId unconditionally; sets discovered_by_scan_id = scanId only when the column is currently NULL (first-discovery sticky — never overwritten once set).

The zero-argument upsert(Discovery) delegates to upsert(d, null) and writes no attribution. All non-scan callers (Docker, passive, ARP) continue to call the zero-argument form and remain completely unaffected.

ScanExecutionService passes the active scan's ID into every upsert call so all devices observed during a scan are attributed to it.

Report endpoint

Path and authentication

GET /api/scans/{id}/report

Requires role VIEWER or ADMIN. Returns HTTP 404 (via NoSuchElementException) when the scan ID does not exist. Implemented in ScanController.report() and delegated to ScanReportService.buildReport(Long scanId).

Delta classification

Each device in the snapshot carries a delta field classifying how it relates to this scan:

Value Meaning Condition
"new" Device was first found by this scan discovered_by_scan_id == scanId
"changed" Pre-existing device re-observed in the scan window At least one service with observedAt in [requestedAt, completedAt]
"unchanged" Pre-existing device with no service re-observed No service observed in the scan window

In-flight scans: when completedAt is null (status PENDING or RUNNING), the upper-bound check on the service window is skipped. Any service observed at or after requestedAt resolves to "changed" rather than causing an error.

Known limitation

Delta is a pragmatic, observation-recency classification derived from service observedAt timestamps. It does not diff stored field values between scans — a device whose IP or hostname changed between two scans will appear as "unchanged" if no service was re-observed in the window. There is no prior-state history; the classification reflects whether the scan touched the device, not what changed about it.

Attribution scope

The device snapshot contains all devices where last_seen_by_scan_id = scanId. This is the full set of devices the scan observed, regardless of whether they existed before the scan. Devices observed by earlier scans but not re-observed by this scan do not appear.

ScanController.getById (the pre-existing GET /api/scans/{id} endpoint) was also updated in V25 to use findIdsByLastSeenByScanId instead of the old time-window query (findIdsByFirstSeenBetween), so both endpoints now use consistent attribution.

Frontend: /scans/:id report page

The scan detail page at /scans/:id (ScanDetailPage) was refactored in V25 to consume GET /api/scans/{id}/report directly, replacing the legacy scan-detail plus per-device lookup flow.

Summary counts bar

A summary bar (testid scan-summary-counts) at the top shows device, service, and CVE counts from summary.

Snapshot table

The device snapshot table (testid scan-snapshot-table) renders one row per attributed device with columns: IP, hostname, service count, CVE count, and a delta badge.

Delta badge colours:

Delta Badge colour
new Green
changed Yellow / amber
unchanged Gray

Export controls

Two buttons appear in the page header:

Button testid Behaviour
Export JSON report-download-json-btn Serialises the full ScanReport to pretty-printed JSON and triggers a browser download named castellum-scan-report-{scanId}.json
Print / PDF report-print-btn Calls window.print() — use the browser's built-in print-to-PDF

The JSON export helper is frontend/src/lib/scanReportExport.ts (exportScanReportJson). It creates a Blob, appends an ephemeral <a> element, triggers the click, and revokes the object URL immediately after download.

API client

api.getScanReport(id: number): Promise<ScanReport>
// GET /api/scans/{id}/report

TypeScript interfaces mirroring the backend DTOs live in frontend/src/api/types.ts: ScanReport, ScanReportSummary, ScanSnapshotDevice, ScanSnapshotService, and the ScanDelta union type ("new" | "changed" | "unchanged").
