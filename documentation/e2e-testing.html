E2E Testing (Playwright)

Running and extending the Castellum Playwright smoke suite

Castellum ships a Playwright smoke suite that covers each major feature group with at least one end-to-end scenario. It runs against a live stack — real Postgres, real Spring Boot backend, real Vite dev server — and is the final safety net between a passing Vitest component run and a production release.

The suite complements, not replaces, the Vitest component tests. Vitest owns unit and component coverage; Playwright owns the integrated, browser-rendered user journey.

Configuration lives in frontend/playwright.config.ts. The Playwright HTML report is written to frontend/playwright-report/.

Prerequisites

Before running the suite locally, ensure:

  1. PostgreSQL 16 is running and accessible (default: localhost:5432).
  2. Backend is running on port 8081 — SERVER_PORT=8081 must be set. See the root .env file and ./mvnw spring-boot:run in the backend/ directory.
  3. Bootstrap admin exists and has already satisfied any forced password-rotation requirements. The suite fails immediately if the admin is flagged mustChangePassword.
  4. Frontend dependencies are installed: bash cd frontend && npm ci
  5. Chromium browser binaries are installed: bash cd frontend && npx playwright install --with-deps chromium

Authentication model

A dedicated setup project runs tests/auth.setup.ts before any spec executes. It logs in as the bootstrap admin, waits for the JWT to appear in localStorage, and calls page.context().storageState({ path: 'playwright/.auth/admin.json' }).

Each feature spec that uses the shared admin session declares:

import { STORAGE_STATE } from './helpers';
test.use({ storageState: STORAGE_STATE });

The pre-existing legacy specs (audit-log, initial-sync-banner, qa-sweep) manage their own login flow and do not opt in to the shared storage state — doing so would break them because those specs navigate to an unauthenticated app entry point and exercise the login screen directly.

The following variables control where the suite points. Defaults are chosen to match a standard local development stack:

Variable Default Purpose
E2E_BASE_URL http://127.0.0.1:5173 Frontend dev server origin (Playwright baseURL)
E2E_API_URL http://localhost:8081 Backend REST API origin
E2E_ADMIN_USERNAME admin Bootstrap admin username
E2E_ADMIN_PASSWORD admin12345 Bootstrap admin password (must match bcrypt hash — see below)
E2E_VIEWER_USERNAME viewer Viewer account username (used by RBAC specs in qa-sweep and initial-sync-banner)
E2E_VIEWER_PASSWORD admin12345 Viewer account password (must match CASTELLUM_VIEWER_PASSWORD_HASH)

The bcrypt pairing — the #1 setup gotcha

The backend reads the admin password hash from the property castellum.admin.password-hash (a bcrypt string stored in application config or set via the CASTELLUM_ADMIN_PASSWORD_HASH environment variable).

The hash must verify against whatever E2E_ADMIN_PASSWORD is set to. If these are out of sync — for example because the password was rotated in the database but the env var was not updated, or because the bcrypt string was regenerated with a different plaintext — the auth.setup step will fail with a login error and every downstream spec will be skipped.

To generate a fresh hash for admin12345 (cost factor 12):

htpasswd -bnBC 12 "" admin12345 | tr -d ':\n' | sed 's/$2y/$2a/'

Store the result as the CASTELLUM_ADMIN_PASSWORD_HASH environment variable (or repo secret) and leave E2E_ADMIN_PASSWORD=admin12345.

Running locally

Run all specs from the frontend/ directory:

# Full suite
npm run test:e2e

# Single spec
npx playwright test tests/cve.spec.ts

# List tests without running
npx playwright test --list

# Open the HTML report after a run
npx playwright show-report

# Install / refresh Chromium binaries
npx playwright install --with-deps chromium

npm run test:e2e is an alias for npx playwright test (added to package.json). The config uses reuseExistingServer: true locally, so if your Vite dev server is already running on E2E_BASE_URL, Playwright will use it rather than start a new one.

CI workflow

.github/workflows/playwright.yml runs on every push to main and on every pull request. The job:

  1. Starts a PostgreSQL 16 service container on port 5432.
  2. Starts the Spring Boot backend on port 8081 with the configured CASTELLUM_ADMIN_PASSWORD_HASH and CASTELLUM_VIEWER_PASSWORD_HASH (read from repo secrets, falling back to a pre-computed bcrypt hash of admin12345). Both the admin and viewer accounts are bootstrapped so that RBAC specs can sign in as either role.
  3. Waits for the backend /actuator/health endpoint to return "status":"UP".
  4. Installs frontend npm deps (npm ci) and Chromium binaries.
  5. Runs npx playwright test with E2E_ADMIN_PASSWORD and E2E_VIEWER_PASSWORD from the matching repo secrets (both fall back to admin12345 when the secrets are absent).
  6. Uploads the HTML report as the playwright-report artifact (retained 7 days) via actions/upload-artifact@v4 — always uploaded, even on failure.

To download the report from a failed CI run: open the workflow summary in GitHub, expand the Artifacts section, and download playwright-report. Unzip and open index.html.

Known limitation — Cytoscape canvas

The topology view renders device nodes on a <canvas> element via Cytoscape.js. Canvas pixels are not part of the DOM; Playwright cannot locate individual nodes, read labels, or simulate clicks on them.

As a result, the topology spec verifies that the canvas element and legend are rendered but does not drive node-click interactions. Decommission flows are instead exercised at the API boundary in decommission.spec.ts — a DELETE /api/devices/:id request is made with a bearer token rather than through the UI dialog — keeping coverage without relying on non-addressable canvas elements.

If node-level UI coverage is needed in the future, consider adding data-testid attributes to a DOM overlay layer that mirrors the canvas graph, or adopting a canvas-testing library.

Adding a new spec

  1. Create frontend/tests/<feature>.spec.ts.
  2. Import { STORAGE_STATE } from ./helpers and call test.use({ storageState: STORAGE_STATE }) at the top if the spec should reuse the admin session.
  3. Use test.step() blocks to document intent at each logical stage.
  4. If the spec needs API-level helpers (login, seed data, trigger actions), add exports to helpers.ts.
  5. Run npx playwright test tests/<feature>.spec.ts locally before pushing.
  6. The CI job picks up new specs automatically — no workflow changes needed.
