Threat-Intelligence Integrations — Operator Runbook

STIX 2.1 export, TAXII 2.1 and MISP integration configuration, reachability probes, curl recipes, AES-256-GCM credential storage, and troubleshooting for Castellum operators.

Section: integrations · Audience: ADMIN operators

This runbook documents how to configure, push, and troubleshoot Castellum's STIX 2.1 export and its TAXII 2.1 and MISP integrations. It covers the STIX bundle shape that flows through the endpoints, the two controllers that expose the surface area, AES-256-GCM credential storage, the reachability probe, and the full troubleshooting matrix for operators.

[INFO] Self-hosted smoke recipe: see docker/README.md for the minimal medallion (TAXII 2.1) and coolacid (MISP) compose stacks plus verbatim request/response captures from the 2026-05-26 smoke run. The credential-rotation procedure that backs the persisted-config path lives in operations.html §7.

Two controllers expose the surface area:

Controller Path prefix Purpose
ThreatIntelController /api/threat-intel/** Stateless one-shot push using server-side defaults (POST /push/taxii, POST /push/misp, POST /export).
IntegrationConfigController /api/integrations/** CRUD over the per-type config row + AES-256-GCM encrypted credentials, plus a POST /{type}/push that decrypts the credential blob and delegates to the same push pipeline, and a POST /{type}/probe reachability check.

All endpoints require ROLE_ADMIN. The frontend Settings page (TAXII / MISP / STIX panel) is just a UI over these controllers.

1. STIX bundle structure

Each export produces one bundle containing:

Object type Source
identity (singleton) Castellum system identity
infrastructure Each discovered device (one per IP)
vulnerability Each CVE associated with a network service
relationship (affects) CVE → device pair
indicator + relationship (targets) Emitted when KEV flag is set OR composite risk score ≥ 7.0

Object IDs are deterministic (UUIDv3 / MD5 namespace) so repeated exports produce identical IDs for the same logical objects. Timestamps use the STIX §3.4 format: yyyy-MM-ddTHH:mm:ss.SSSZ.

2. Stateless export & push endpoints

ThreatIntelController exposes a stateless surface that uses the server-side default configuration. All three endpoints require ROLE_ADMIN.

Method Path Description
POST /api/threat-intel/export Return bundle as application/json
POST /api/threat-intel/push/taxii?collection=<id> Push bundle to configured TAXII collection (optional override)
POST /api/threat-intel/push/misp Push bundle attributes to a MISP event

Export response

HTTP 200 application/json
{ ...stix bundle JSON... }

TAXII push response

{ "status": "pushed", "objects": 12, "bundle_id": "bundle--…", "status_code": 201 }

MISP push response

{ "status": "pushed", "bundle_id": "bundle--…", "misp_event_id": "42" }

Error responses

HTTP Cause
502 Bad Gateway Upstream TAXII or MISP server unreachable or returned an unexpected response
403 Forbidden Caller does not have ADMIN role

Every push attempt (including failures) is recorded in the threat_intel_push table and in the audit log (see §9).

curl recipes

All recipes assume :8081 and an admin Bearer token already obtained via POST /api/auth/login. Set $TOKEN before running.

# Login to obtain $TOKEN
TOKEN=$(curl -s -X POST http://localhost:8081/api/auth/login \
  -H "content-type: application/json" \
  -d '{"username":"<admin-username>","password":"<admin-password>"}' \
  | python3 -c 'import json,sys;print(json.load(sys.stdin)["token"])')
echo "$TOKEN" | head -c 24 ; echo

The admin user / password hash are seeded at boot from castellum.admin.username + castellum.admin.password-hash (BCrypt) — see BootstrapAdminInitializer. There is no compiled-in fallback admin.

# Push via the stateless ThreatIntel endpoint (no config row needed)
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8081/api/threat-intel/push/taxii?collection=<override-uuid>"

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:8081/api/threat-intel/push/misp

# Export-only (returns the STIX bundle inline)
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:8081/api/threat-intel/export | python3 -m json.tool | head -40

UI equivalent — Settings page export panel. The STIX Export section of the Settings page (StixExportPanel) provides two ADMIN-only controls; VIEWER role sees neither:

  • Download STIX bundle — triggers the export endpoint and saves the result as stix-bundle-<timestamp>.json.
  • Preview bundle — fetches the bundle text via exportStixBundleText() and renders it as pretty-printed JSON (JSON.stringify(…, null, 2)) in a scrollable on-screen block. Indentation is applied client-side only; the wire format remains compact JSON.

Both controls share a busy lock so only one operation runs at a time. Errors appear inline below the buttons.

3. Encryption — CASTELLUM_INTEGRATION_KEY

Persisted credentials are encrypted at rest with AES-256-GCM (AesGcmCipher).

  • Source env var: CASTELLUM_INTEGRATION_KEY
  • Property name: castellum.integration.key
  • Value: base64-encoded 32-byte (256-bit) key
  • Generate one with: bash openssl rand -base64 32
  • If unset, the application boots but every PUT /api/integrations/{type} (which encrypts) and every POST /api/integrations/{type}/push (which decrypts to verify the row is still readable) fails with IllegalStateException: CASTELLUM_INTEGRATION_KEY is not configured — set a base64 AES-256 key.
  • Invalid base64 fails fast at boot with CASTELLUM_INTEGRATION_KEY is not valid base64.
  • A key that decodes to anything other than 32 bytes fails at boot with CASTELLUM_INTEGRATION_KEY must decode to <expected> bytes.

The AesGcmCipher uses a 12-byte random IV per record and a 128-bit GCM authentication tag. Each row in integration_config stores the IV concatenated with the ciphertext blob (column type BYTEA on Postgres, VARBINARY(4096) on the H2 test profile). Decryption failures surface as a 500 so a wrong CASTELLUM_INTEGRATION_KEY after rotation fails loud rather than silently misbehaving.

Key rotation: there is no automatic re-encrypt-on-key-change path. Rotating the key invalidates existing rows; the POST /{type}/push decrypt-probe will throw, and the operator must re-PUT the config to re-encrypt under the new key. The full "truncate + re-enter" rotation procedure is documented in operations.html §7.

4. PUT /api/integrations/{type} — JSON shape

Request body schema (from IntegrationConfigDto.SaveRequest):

{
  "config":      { "...": "free-form JSON, persisted as-is in config_json" },
  "credentials": "string — encrypted and stored as encrypted_credentials (bytea)"
}

Both fields are optional:

  • config: null → persisted as "{}".
  • credentials: null → persisted as cipher.encrypt("") (a non-empty ciphertext over an empty plaintext; credentialsSet returns false only if the byte array is null/empty).

{type} is normalized to upper-case and must be one of TAXII or MISP. Anything else returns 400 with body unsupported integration type: <input> (expected TAXII or MISP).

4.1 TAXII

Recommended config keys (consumed by the push path):

Key Read by Notes
collectionId IntegrationConfigController.push Forwarded to ThreatIntelService.pushTaxii(collection) as the target collection override. If absent or null, the server uses its compiled-in default.

credentials is whatever bearer / basic token the operator's TAXII server expects. Note: the value is stored encrypted, but ThreatIntelService.pushTaxii currently uses env-injected credentials at runtime — the persisted credentials field is decrypted only as a readability probe before the push. Treat the persisted value as the source of truth for "is the key still good?" not as the live transport credential.

Example body:

{
  "config": { "collectionId": "1f33c1cc-8b66-4f10-9c4f-8c92e0e3a4e2" },
  "credentials": "Bearer eyJhbGciOiJIUzI1NiJ..."
}

# Save TAXII config
curl -s -X PUT http://localhost:8081/api/integrations/TAXII \
  -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "config": { "collectionId": "<your-taxii-collection-uuid>" },
    "credentials": "Bearer <your-taxii-token>"
  }'

4.2 MISP

config is currently unread by the push path — ThreatIntelService.pushMisp() takes no parameters from the persisted row. Persist {} (or any operator-facing notes — they will round-trip through the response) and put the live MISP transport creds in env vars consumed by the MISP client.

Example body:

{
  "config": { "note": "prod MISP instance, contact ops" },
  "credentials": "<MISP API key — stored encrypted, used as a readability probe>"
}

# Save MISP config
curl -s -X PUT http://localhost:8081/api/integrations/MISP \
  -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "config": {},
    "credentials": "<your-misp-api-key>"
  }'

4.3 Response shape

IntegrationConfigDto.Response (returned by PUT and GET):

{
  "id": 1,
  "integrationType": "TAXII",
  "config": { "...": "as persisted" },
  "credentialsSet": true,
  "lastPushAt": null,
  "lastPushStatus": null,
  "createdAt": "2026-05-26T12:00:00Z",
  "updatedAt": "2026-05-26T12:00:00Z"
}

The encrypted bytes are never serialized — credentialsSet is the only signal exposed.

# Inspect persisted config (no secrets returned)
curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8081/api/integrations/TAXII | python3 -m json.tool

4.4 Reachability probe

POST /api/integrations/{type}/probe (ADMIN) performs a bounded-timeout connectivity check against a candidate TAXII 2.1 or MISP endpoint before the operator saves it. Body: { "url": "…", "collectionId": "…" } (collectionId optional, TAXII only). Returns { "reachable": <bool>, "detail": "…" }.

Any HTTP response — including 401 / 403 from an auth-gated server — counts as reachable: true; only connection-refused / host-unreachable and read timeouts return reachable: false. Timeouts are tunable via castellum.integration.probe.connect-timeout-ms (default 3000) and castellum.integration.probe.read-timeout-ms (default 5000). The probe is read-only and persists nothing.

# Probe a candidate TAXII endpoint before saving it
curl -s -X POST http://localhost:8081/api/integrations/TAXII/probe \
  -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" \
  -d '{ "url": "https://cti-taxii.mitre.org/taxii/", "collectionId": "<collection-uuid>" }' \
  | python3 -m json.tool

4.5 Config presets and auto-detect (admin UI)

TaxiiConfigPanel and MispConfigPanel offer one-click presets that fill the URL — and, for TAXII, the collection id — in a single selection (e.g. the MITRE ATT&CK TAXII root https://cti-taxii.mitre.org/taxii/, or CIRCL MISP https://misp.circl.lu/). Selecting a preset immediately fires the reachability probe above and renders a reachability indicator beside the field; when a known server is recognised from the entered URL the panel surfaces an "auto-detected" note. In a Docker-compose dev stack the panels prefill the bundled TAXII / MISP service URLs while the saved config is still blank.

5. POST /api/integrations/{type}/push — empty-config behavior

Behavior matrix when the config row does not exist:

Precondition Response
No row for {type} saved 404 with NoSuchElementException body integration_config not found for type: <NORMALIZED>
Row exists, but CASTELLUM_INTEGRATION_KEY missing or rotated 500 path — cipher.decrypt(...) throws IllegalStateException before any upstream push is attempted. The lastPushStatus is not updated in this path (the throw is before the try/finally).
Row exists, decrypts OK, upstream push fails 200 with body { "status": "error", "bundleId": null, "pushedAt": "<now>", "lastPushStatus": "ERROR: <truncated message ≤ 200 chars>" }. Row's lastPushAt / lastPushStatus are persisted; audit event TAXII_PUSH or MISP_PUSH recorded with status: ERROR.
Row exists, decrypts OK, upstream push succeeds 200 with body { "status": "ok", "bundleId": "<uuid>", "pushedAt": "<now>", "lastPushStatus": "SUCCESS: ..." }. Audit event recorded with status: SUCCESS.

Anonymous probe captured against the local backend:

$ curl -s -o /tmp/r -w "HTTP %{http_code}\n" -X POST http://localhost:8081/api/integrations/TAXII/push
HTTP 401
$ cat /tmp/r
{"status":401,"path":"/api/integrations/TAXII/push","error":"unauthorized"}

So the auth gate is the first line — a missing token short-circuits before any config-lookup or decrypt logic runs.

# Push via the persisted-config endpoint
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:8081/api/integrations/TAXII/push | python3 -m json.tool

6. Configuration surfaces

Two configuration surfaces are supported. Pick exactly one — they are mutually exclusive:

  1. integration_config table (V15 migration) — the recommended path. Credentials are stored in Postgres encrypted at rest with AES-256-GCM. Managed through the admin UI (TaxiiConfigPanel, MispConfigPanel) or directly through GET / PUT /api/integrations/{type}. The encryption key comes from CASTELLUM_INTEGRATION_KEY (§3); without that env var, the application refuses to load any encrypted row at boot.
  2. Environment variables (legacy) — the pre-V15 path, still honoured for ops parity. Credentials live in plaintext in the process env. Avoid for new deployments.

Environment-variable form (legacy)

# TAXII 2.1
TAXII_BASE_URL=https://taxii.example.com
TAXII_COLLECTION_ID=<default-collection-id>
TAXII_USERNAME=<user>
TAXII_PASSWORD=<pass>

# MISP
MISP_BASE_URL=https://misp.example.com
MISP_API_KEY=<api-key>
MISP_DISTRIBUTION=0       # 0=organisation only; 1=community; 2=connected; 3=all
MISP_THREAT_LEVEL_ID=2    # 1=high; 2=medium; 3=low; 4=undefined

Corresponding application.yml keys:

castellum:
  taxii:
    base-url: ${TAXII_BASE_URL:}
    collection-id: ${TAXII_COLLECTION_ID:}
    username: ${TAXII_USERNAME:}
    password: ${TAXII_PASSWORD:}
    backoff-base-millis: 6000
  misp:
    base-url: ${MISP_BASE_URL:}
    api-key: ${MISP_API_KEY:}
    distribution: ${MISP_DISTRIBUTION:0}
    threat-level-id: ${MISP_THREAT_LEVEL_ID:2}
    backoff-base-millis: 6000

7. Retry behaviour

Both TaxiiClient and MispClient retry up to 3 times on 5xx responses using exponential back-off. The back-off base is configurable (backoff-base-millis; default 6 s, matching NvdClient). Non-retryable errors (4xx, network reset) propagate immediately as IOException.

8. Troubleshooting

Symptom Likely cause What to check
401 on every endpoint Bearer token missing or expired. Re-run the login recipe (§2). Confirm Authorization: Bearer <token> header is present on the failing request.
403 on /api/integrations/** Caller has ROLE_VIEWER, not ROLE_ADMIN. Re-issue the token from an admin account. The frontend Settings page intentionally hides the panel for viewers.
404 integration_config not found No PUT /api/integrations/{type} has been done since boot (or DB reset). Save the config first (§4.1 / §4.2) before calling /push.
400 unsupported integration type Path variable is not TAXII or MISP. Case-insensitive — taxii works, STIX does not. Use upper-case TAXII / MISP for clarity.
500 with CASTELLUM_INTEGRATION_KEY is not configured Env var missing on the running JVM. printenv CASTELLUM_INTEGRATION_KEY on the backend host. Set, restart, re-PUT the config so the row is re-encrypted under the live key.
500 with AES-GCM tag-mismatch / GeneralSecurityException Key was rotated and the existing row was encrypted under the previous key. Re-PUT the config row to re-encrypt under the new key. There is no auto-migration path.
200 with status: "error" from /{type}/push Auth gate + decryption succeeded but the upstream TAXII/MISP server rejected or timed out. Inspect lastPushStatus on the row (GET /api/integrations/{type}). The error message is truncated to 200 chars — full stack trace lands in the backend log. Audit-log row also captures status: ERROR + truncated message.
Push hangs (no response) Upstream TAXII/MISP server unreachable; the HTTP client doesn't have an aggressive timeout in some paths. Check network reachability + the upstream server's logs. Run the reachability probe (§4.4) against the URL. Cancel the request from the client side; the backend transaction rolls forward with lastPushStatus = "ERROR: ..." once the underlying call eventually throws.
credentialsSet: false after a PUT Body had credentials: null (or omitted). Include a non-empty credentials string in the PUT body. An empty string is encrypted but still produces a non-empty ciphertext, so credentialsSet would still read true — false specifically means the bytea column is null/zero-length.

9. Audit / push log

The threat_intel_push table captures every push attempt:

Column Description
push_target TAXII, MISP, or EXPORT
bundle_id STIX bundle id field
status_code HTTP status code returned by upstream
response_excerpt First 1 KB of upstream response body
occurred_at Timestamp (defaults to now())
audit_log_id FK to matching audit_log row

Query recent pushes:

SELECT push_target, bundle_id, status_code, occurred_at
FROM threat_intel_push
ORDER BY occurred_at DESC
LIMIT 20;

11. Live integration testing

The unit tests use MockRestServiceServer surrogates. For a real end-to-end test:

  1. Start a local TAXII server (e.g. medallion): bash docker run -p 5000:5000 oasis-open/medallion
  2. Set TAXII_BASE_URL=http://localhost:5000 and a valid collection ID.
  3. POST to /api/threat-intel/push/taxii and confirm a 201 response.

For MISP:

docker compose -f docker/misp-minimal.yml up -d

Then set MISP_BASE_URL and MISP_API_KEY and POST to /api/threat-intel/push/misp.

12. Out of scope

  • Standing up a real TAXII 2.1 server (e.g., mitre/cti-taxii-server) or a MISP instance for round-trip verification. The runbook assumes the operator has these endpoints already and only documents the Castellum side of the wire.
  • Multi-tenant or multi-endpoint per-type configs. The current schema is one row per integration_type (TAXII / MISP) — a deployment with two TAXII servers needs a schema change.
  • Re-encryption automation on key rotation.
